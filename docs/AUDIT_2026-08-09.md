## 1. Headline

**The last audit's headline finding is half-answered, and the half that answered is the half
that was acted on.** `AUDIT_2026-08-08.md` §1 observed that the gate had never gone red in
73/73 runs — *"a green signal from a gate with no demonstrated ability to fail carries much
less information than its volume suggests."* Since then the gate has gone red **five times
across four different steps** — `guard-ablation` (×2), `requires`, `bash32-scan`,
`skill-manifest` — and three of those four are steps the M-5a / M-5b / SC-12 remediation wave
added in answer to that very finding. The mechanisms built to be falsifiable proved
falsifiable on real work, within a day of shipping.

The eleven steps that have never gone red — including `parity`, the 108-fixture suite that is this project's
flagship verification asset — remain 0-for-139. §3 argues why that is mostly fine and
precisely where it is not.

**The pipeline's detection half is in good shape; its retention half is what SC-13 just
fixed.** Jobs 0003/0004 found eleven real defects and repaired ten, with five Critic `fail`
verdicts that were **true positives five times out of five**, and shipped nothing. SC-13
closed six of the seven findings. This audit does not re-litigate that; it looks at what the
same evidence says about the three areas SC-13 did not touch.

**Three things this audit found that no prior one did:**

1. **`SKILL.md` has no line budget, and SC-10's considered floor was erased in 24 hours.**
   SC-10 cut it to 337 and explicitly rejected going further. SC-11/12/13 put back **+87
   lines** — the entire reduction — across three scope changes in about a day. The lint
   NOTEs at 350 and fails at 500. At the observed rate the NFR-3 ceiling arrives in roughly
   three more scope changes. (F-83)
2. **The mechanism built to detect unpinned rules now files them, in fields it never reads.**
   All **19** accepted guard-ablation survivors carry `class: "unpinned"` and
   `owner: "SC-12 (unscheduled)"` — a bulk assignment, made after SC-12 shipped without
   closing one, in two fields `guard-ablation.mjs` never reads. Because nothing read them,
   the register was wrong in both directions at once: a provably dead branch filed as debt,
   and a real gap filed identically. The real gap is the legacy YELLOW band — **and the pack
   contains a fixture named `legacy-yellow-zone.json` whose entropy lands it in the RED
   band**, so deleting the yellow rule left it green. F-71's exact shape, found live in the
   mechanism built to answer F-71. (F-86)
3. **SC-13's own Critical finding shipped as prose with nothing asserting it.** The "never
   evaluate `reproduction.command`" rule lives at `artifact-layout.md:348` and nowhere else —
   not a `SKILL.md` hard rule, not in the agents' security block, no lint. That is F-55 (*"a
   rule nothing asserts is a rule nothing enforces"*) and F-75 (*"a field the reader is not
   told to read is a field that was not written"*) recurring **inside the scope change that
   fixed both**. (F-82)

## 2. Confirmed findings (reproduced)

Every citation below was opened against this checkout, not inferred.

### F-80 — Tier-3 review egress trusts an unvalidated `OLLAMA_HOST`

`scripts/local-ci/review.sh:31`:

```sh
OLLAMA="${OLLAMA_HOST:-http://localhost:11434}"
```

and `:73` posts the branch diff to it:

```sh
if out="$(printf '%s' "$req" | curl -sf "$OLLAMA/api/chat" -d @- …
```

There is no validation between the two. The default is loopback, and the body goes via
`curl -d @-` so the diff never reaches the process table — both deliberate and both correct.
But any environment that sets `OLLAMA_HOST` (a copied dotfile, a shared shell profile, a
poisoned CI env, a teammate's `.envrc`) silently ships the **full branch diff** to an
arbitrary host, with no output naming the destination. This is the only network egress in the
repository, which is what makes it worth a guard rather than a note.

Recorded as an observation in `AUDIT_2026-08-08.md` §6 (*"`OLLAMA_HOST` is an unvalidated env
var"*); no fix shipped.

### F-81 — secret redaction is LLM-honoured, and SC-11 + SC-13 widened its blast radius

`references/agent-shared-blocks.md:41-50` requires all ten agents to redact secrets
(`[REDACTED]`) before writing them to any evidence file. `agent-blocks-lint.mjs` proves that
all ten carry the same *text* — byte-identically, across three blocks — and cannot prove any
agent obeys it. `SC10_PLAN.md` §6 already recorded this: *"That gap is real and unaddressed."*

**What changed since that entry, and why it is now worth more than a note:**

- SC-11/A5 made every terminal run write `artifacts/{jobId}.tar.gz` to
  `execution.evidence_archive_dir` — a durable destination **outside the worktree and outside
  the target checkout**, verified by extraction. Before SC-11, unredacted material in an
  evidence tree died with the worktree at teardown.
- SC-13/F-77 added `consensus/repro/` — **verbatim copies of target-repo files** — to that
  same tree. `artifact-layout.md:338` states the consequence plainly: *"so it lands in the
  evidence tree and therefore in the terminal archive."*

Both changes are correct and this audit does not propose reversing either. The point is that
the archive is now a durable, growing, off-checkout corpus of untrusted-repository content
whose only redaction control is an instruction to a language model. The pipeline's own
history is unkind to that class: F-2, F-28/F-29 and F-54 are all cases where a *lexical* rule
misjudged content, and the agents' rule is weaker than lexical.

### F-82 — the "never evaluate `reproduction.command`" rule is prose in one reference file

SC-13's review classified a free-form shell string, composed by an agent that has just read an
untrusted repository, as **Critical**. The resulting rule is good and complete
(`artifact-layout.md:344-352`):

> **Never pass `command` to a shell, `exec`, or any evaluating API.** … Anything automated
> must go through an allowlisted runner keyed by `check_id`, never through this string.

It is also the only place the rule exists. It is **not** a `SKILL.md` hard rule; it is **not**
in the agents' security block (verified — that block covers prompt injection and secret
redaction only); and no lint asserts it. Nothing executes the string today, which is exactly
the condition under which SC-13 said to write the rule — but the rule was then placed in a
reference file that the orchestrator reads on demand, guarding a field that a future
automation author would meet in a schema, not in prose.

The `files` half of the same rule (`resolveWithinRoot`, reject absolute paths / `..` /
escaping symlinks) has the same status.

### F-83 — `SKILL.md` has no line budget, and SC-10's floor was erased in 24 hours

Measured across all 26 commits that touch the file (table in §4). The shape:

| Milestone | Lines | Δ |
|---|---|---|
| SC-9 (2026-08-08) | 425 | high-water mark |
| **SC-10 (2026-08-08)** | **337** | **−88, deliberate** |
| SC-11 | 359 | +22 |
| SC-12 (+A5) | 378 | +19 |
| SC-13 (+review fixes) | **424** | +46 |

SC-10 did not merely shrink the file; it **decided where the floor was** and recorded the
reasoning (`SC10_PLAN.md` §5, "Rejected"):

> **Cutting `SKILL.md` to the ~285 originally sketched.** The remaining compression targets
> are restatements of gate rules that the orchestrator acts on directly. **337 with a
> 350-line advisory target is where the prose stops being reference-grade.**

Three scope changes then put back all 88 lines in about 24 hours. No one overrode that
decision; nobody was asked to. `frontmatter-lint` emits `NOTE — SKILL.md is 424 lines, over
the 350-line target (ceiling is 500)` and passes.

**This finding is not "compress it again."** SC-10 rejected that on good grounds and this
audit does not reopen it. The finding is that 337 was a *decision with no mechanism*, and a
target that only NOTEs is a target that records drift rather than bounding it. At the observed
~+29 lines per scope change, NFR-3's 500-line ceiling — which is also the authoring guidance's
limit — arrives in roughly three more.

**The growth was already noticed once, and the response bounded the wrong thing.** M-3b
(F-42, `DPPD.md` §17) observed the file at *"357 (SC-4), 367 (SC-5), 379 (SC-6),
**monotonic**"* and fixed the right half of the problem: NFR-3 had been verified by a human
running `wc -l`, so `frontmatter-lint.mjs` was made to assert it. What it asserted was the
**500 ceiling** — the point at which the file is already too large — not the trend that was
the actual observation. Two months on, the trend is unchanged (25 growths, 1 reduction in 26
commits) and the ceiling still has not been hit, so the lint has never had anything to say.

SWEBOK v4 §7 frames the general case: a threshold that is not enforced at the moment of change
is a measurement, not a control. The project already knows this in its own words — F-55's
*"a rule nothing asserts is a rule nothing enforces."*

### F-84 — input-dimension coverage has no owner

Named "Still open" by `DPPD.md` §22 and by the issue-#24 field record's "Carried forward."

Nine Critic rounds across jobs 0003/0004 never varied the manifest-count axis. Defect 9 was
reachable **only** with a two-document manifest; all 24 frozen fixtures, both checked-in
tests, and every prior Critic round used single-document manifests. The record's own summary:

> Nine rounds missed multi-document manifests because no artifact anywhere said "manifests can
> name more than one document."

Nothing in the task contract, in `criteria-to-checks`, or in any agent definition enumerates
the input dimensions of a change set. `criteria-to-checks` derives checks from criteria prose,
and criteria prose does not enumerate input shapes. F-76 now makes a *repaired* defect leave a
regression check behind; it does nothing about the axis nobody has varied yet. The defect
count fell at roughly the rate an adversary happened to stumble into new territory.

This is the same class as F-70 (*a fixture-scoped criterion set makes the grader structurally
blind*): in both, the artifact that bounds what can be checked is upstream of every mechanism
that does the checking.

### F-85 — cross-job memory is manual

Named "Still open" by `DPPD.md` §22.

SC-13/F-73 gives a successor job a **classified worktree** — every path typed `unchanged` /
`changed` / `added` / `removed`, with `unchanged` carrying gate evidence only as far as
`gated_through` reached. It does not carry the predecessor's *findings*. Job 0004 re-confirmed
0003's eight defects only because the operator wrote it into a free-text `operator_notes`
paragraph — the same improvisation-in-prose that F-73 exists to end, surviving one layer up.

`run_manifest.carry_over` already exists, already carries per-file digests, and is already
written on every non-PROMOTE terminal state. It is the natural carrier, and F-76 has just
created the thing worth carrying: `regression_check_id`s in the `REG-…` namespace.

### F-86 — all 19 accepted survivors are unverified rules, owned by a shipped work package, in fields the tool never reads

`guard-ablation.mjs` exists because of F-71 (*"a frozen fixture can pin nothing, and the pack
looks identical either way"*). A survivor means the mutated rule is pinned by nothing. The
baseline's `_doc` states the taxonomy precisely:

> Every entry must carry `reason` and `class`. `class: equivalent` means the mutation provably
> cannot change behaviour. `class: unpinned` means the rule genuinely lacks a fixture and MUST
> carry an `owner` naming the work package that closes it.

Against that contract, four facts about the current baseline:

**1. All 19 accepted entries are `class: "unpinned"`. Not one is `equivalent`.** By the
baseline's own definition, the file records **nineteen rules that genuinely lack a fixture** —
not a list of provably-harmless mutations with a few gaps mixed in. Twelve carry a `reason` of
*"Defensive input guard on a helper the fixture corpus only ever reaches with well-formed
input"* and seven *"Branch the fixture corpus never reaches"*; both prose forms sit inside
`class: unpinned`, and the class field is the authority.

**2. All 19 carry `owner: "SC-12 (unscheduled)"`.** SC-12 shipped on 2026-08-08 (`DPPD.md`
§21) and closed none of them. The field that exists to name the work package that closes a gap
now names a work package that has completed. Nothing signalled the lapse, because —

**3. `guard-ablation.mjs` never reads `class` or `owner`.** Neither identifier appears
anywhere in the tool. Both fields are written into the baseline, required by its `_doc`, and
consumed by nothing. That is F-75 (*a field the reader is not told to read is a field that was
not written*) and recurring mode #9 (*a count no consumer compares is not a control*), inside
the file built to answer F-71.

**4. "This list may only SHRINK" is enforced against staleness, not against growth.** The two
rules the `_doc` says are tool-enforced genuinely are (`guard-ablation.mjs:379-399`): an
unaccepted survivor fails, and a stale entry fails. Neither prevents the list from *growing* —
a new survivor added to `accepted` in the same commit passes the gate. The shrink-only property
is convention, not control.

Distribution of the nineteen: `drift-sentinel` **13**, `task-normalize` 3,
`criteria-to-checks` 2, `review-risk-assess` 1. `drift-sentinel` is the verify-phase
validator whose verdict drives the post-ship drift BLOCK (`SKILL.md` §4), and it holds 13.

The gate's success line reads `OK — every survivor is an accepted baseline entry (19)`, which
is true and reads as clean. Nineteen entries the file itself calls unverified rules are being
reported as a pass.

#### What the SC-14 triage found — and one correction to this audit's first cut

This section originally singled out `drift-sentinel:verdict:#5` (`drift-sentinel.js:452`,
`'fail' → 'pass'`) as *"a verdict-affecting rule in the post-ship gate that no fixture can
falsify."* **That was wrong, and the remediation found it.** Every return path in `computeCTM`
— the early short-history return and all four band returns — sets `zone` to exactly one of
`green` / `yellow` / `red`, so the `else` that mutation touches is dead code. Branch
instrumentation confirmed it is entered by none of 210 probe inputs across both gating modes.
It is a defensive default on an unreachable branch: `class: equivalent`, and the register
overstated the debt there rather than understating it.

A 931-input sweep across both gating modes re-triaged the `drift-sentinel` entries. It found
**exactly one genuinely unpinned and reachable rule** — and that one is sharper than the
claim it replaces:

**The legacy YELLOW band was pinned by nothing, and the pack contains a fixture named for
it.** `legacy-yellow-zone.json` ("returns warn when entropy puts CTM in yellow zone") has
entropy `0.25`, giving `ctm = 0.33 − 0.25 = 0.08` — below `CTM_YELLOW` (0.1). It lands in the
**red** band, and its own frozen expectation says so: `zone: "red"`, `risk_level: "high"`.
Deleting the yellow rule entirely left that fixture green. **A fixture named for the rule it
does not pin is F-71's exact shape, found live in the mechanism built to answer F-71.**

So the corrected finding is not "13 unverified rules in the post-ship validator." It is:

- the taxonomy is right and the assignment was **bulk**, not per-entry — which is why it was
  simultaneously too harsh (a dead branch filed as debt) and too lax (a real gap filed
  identically, with no owner who would ever close it);
- nothing read the fields, so neither error had any consequence;
- one real gap existed, and the fixture that should have caught it was named for it.

**A further limitation the triage hit:** the baseline's `mutation` field is **truncated with an
ellipsis** for long conditions (`if (!Array.isArray(entropyHistory) || entropyHistory.length <… → if (false)`).
Two entries could not be replayed from the file at all. A register whose entries cannot be
reconstructed from the register is a register you must re-derive to audit.

### F-87 — reference cross-linking creates the nested-read hazard; one reference lacks a TOC

All seven reference files are indexed one level from `SKILL.md`, and `frontmatter-lint` checks
that **bidirectionally** (every referenced path exists; every reference file is indexed). That
is correct and better than the authoring guidance asks for.

But five of the seven also cross-link **each other**, and the two largest reference each other
circularly:

| File | Lines | Links to |
|---|---|---|
| `phase-gates.md` | 601 | `artifact-layout.md`, `agent-shared-blocks.md` |
| `artifact-layout.md` | 473 | `phase-gates.md` |
| `runtimes.md` | 68 | `phase-gates.md` |
| `task-contract.md` | 139 | `validator-inputs.md` |
| `validator-inputs.md` | 132 | `artifact-layout.md` |

The authoring guidance's reason for the one-level rule is mechanical, not stylistic: a file
reached *through* another reference tends to get previewed (`head -100`) rather than read.
For a 601-line gate reference, a partial read is a correctness risk. The existing TOCs
mitigate this — six of seven files have one — which is why this is a small finding rather
than a large one.

The exception: **`validator-inputs.md` (132 lines) is the only reference over 100 lines with
no `## Contents` block**, and it is reachable through `task-contract.md`.

CLI-shape assertions whose falsification was demonstrated by hand in `SC10_PLAN.md` §4 rather
than in the ledger. That is adequate; recorded so it is not mistaken for the `parity` case.

**CI is not a performance problem.** The Tier-1 gate is ~15 s wall clock across 15 steps
(`parity` ~5 s, `cli-contract` ~3 s, everything else ≤ 2 s). Nothing in this audit proposes
optimizing it, and any remediation that adds a step has real budget to spend.

## 6. Security posture: what holds

Re-verified against this checkout during this audit, not carried forward. Recorded so
remediation does not disturb it.

- **The prototype-pollution class is closed systematically, not locally.** SC-9/A1(a) fixed
